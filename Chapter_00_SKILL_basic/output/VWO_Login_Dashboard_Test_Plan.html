1. Objective

Verify that the VWO login experience provides secure, reliable, accessible, and low-friction entry to the experimentation platform for marketers, product managers, UX designers, developers, enterprise teams, CRO specialists, and analysts.

Testing will assess the requirements in the supplied PRD, including email/password authentication, optional MFA, enterprise SSO, password recovery, remembered sessions, responsive and accessible UI, security controls, integrations, and the stated performance and business targets.

Requirement baseline: This plan is based only on the supplied PRD and the attached test-plan skill. The PRD identifies https://app.vwo.com/login as the login page. Environment URLs, test accounts, supported browser versions, sprint dates, load profiles, and named approvers were not supplied and remain TBD.

2. Scope

In scope

  • Functional and end-to-end testing of login, validation, remember-me behavior, success/error states, and post-login dashboard transition.
  • Password recovery and reset, including secure token lifecycle and password requirement enforcement.
  • Optional 2FA and enterprise SSO flows (SAML, OAuth, and supported organizational configurations), when available in the test environment.
  • UI, usability, responsive layout, light/dark theme, keyboard access, screen-reader semantics, high contrast, and WCAG 2.1 AA checks.
  • Security verification of HTTPS, session handling, rate limiting, access control, error disclosure, and authentication-data handling. Backend storage and compliance controls require evidence review with the responsible engineering/security teams.
  • Integration checks for VWO core platform, login analytics, support assistance, social identity providers, and onboarding/marketing services where enabled.
  • Performance, load, availability, cross-browser/device, regression, smoke, sanity, exploratory, and monitoring checks.

Out of scope / future enhancements

  • Biometric authentication, adaptive/risk-based authentication, and progressive web app capabilities, listed by the PRD as future enhancements.
  • Testing VWO experimentation, personalization, and analytics features beyond login handoff, session/context preservation, and the integrations stated in this plan.
  • Production load generation, penetration testing, or security testing that could affect real users without explicit authorization, approved limits, and a designated environment.

5. Defect Reporting Procedure

Log defects in JIRA (tool specified by the skill template). Report any mismatch with the PRD, failed user journey, accessibility barrier, security concern, unexpected data/session behavior, or performance target miss.

  1. Create a JIRA issue with concise title, environment/build, browser/device, account/role where safe, preconditions, numbered reproduction steps, expected and actual results, severity/priority, and evidence such as screenshots, HAR/log excerpts, or timestamps.
  2. Do not attach passwords, reset tokens, session cookies, or personal data. Redact sensitive values before adding evidence.
  3. Triage with QA, product, engineering, and security as appropriate; assign an owner and disposition. Security-sensitive issues should use the approved restricted reporting path if one exists (process TBD).
  4. Retest fixes in the target environment, record the result, and run related regression coverage. Keep the issue open if the fix is incomplete or causes a regression.
  5. Share a daily end-of-day defect/status summary with development management during active execution, following the skill template.

6. Test Strategy

  1. Analyze and design: Review and clarify PRD requirements; map requirements to scenarios and test cases; prioritize by user impact and security risk. Apply equivalence partitioning, boundary-value analysis, decision tables, state-transition testing, use-case testing, and error guessing.
  2. Shift-left checks: Review requirements, UX flows, accessibility expectations, security assumptions, event tracking, and acceptance criteria before the build is declared ready.
  3. Smoke and sanity: On each candidate build, verify page access, core login, failure handling, recovery entry point, and successful dashboard handoff. Reject the build for in-depth testing if smoke checks fail.
  4. Functional and end-to-end: Execute prioritized cases for login, recovery, sessions, MFA/SSO, integrations, validation, and error recovery. Use controlled accounts and approved test data.
  5. Non-functional: Run compatibility, responsive, usability, WCAG 2.1 AA, security-control, performance, load, and monitoring checks in approved environments. Coordinate evidence-based review for backend hashing, GDPR/CCPA, audit, and infrastructure claims that cannot be confirmed through UI behavior alone.
  6. Regression and exploratory: Retest fixes and repeat relevant regression suites. Explore interrupted flows, repeated submissions, network loss/recovery, expired links/sessions, and unusual but valid input combinations.
  7. Reporting and iteration: Track execution and defects in JIRA, issue daily status summaries, review leading and lagging indicators, and repeat test cycles until exit criteria are met or risks are formally accepted.

Metrics and guardrails

  • Leading indicators: smoke pass rate, planned-vs-executed cases, blocked cases, open P0/P1 defects, login/recovery flow completion in test runs, and performance trend by build.
  • Lagging indicators / PRD targets: login success rate of at least 95%; user satisfaction of at least 90%; login-related support tickets reduced by 20%; page load below 2 seconds on the agreed standard connection.
  • Guardrails: zero successful brute-force attacks or unauthorized access; no session-hijacking incidents; 100% compliance with applicable security audit requirements; no release with unresolved critical security or access-control defects.

Define metric instrumentation, measurement windows, baselines, sample sizes, and the exact load profile with product/engineering before execution. Business KPI outcomes may require post-release monitoring and are not established solely by a pre-release test run.

9. Entry and Exit Criteria

Requirement analysis

Entry: Testing team has received the PRD and relevant project details.

Exit: Requirements are reviewed and understood; open questions, measurable acceptance criteria, environment needs, and dependencies are recorded with owners.

Test design

Entry: Scope and requirements are available for review.

Exit: Prioritized scenarios/cases and traceability are prepared and reviewed; required test data, accounts, SSO/MFA setup, and environment access are identified.

Test execution

Entry: Test scenarios/cases are signed off; application build and environment are available; test accounts/data and required integrations are configured; smoke testing passes.

Exit: Planned in-scope execution is complete or exceptions are documented; defects are logged and triaged; fixes are retested; no unresolved Critical defects or unacceptable security/access-control risks remain; performance and accessibility findings are assessed against agreed criteria.

Test closure

Entry: Test execution results and defect reports are ready.

Exit: Test summary is submitted; residual risks, deferred cases, and accepted defects have owners and approval; deliverables are reviewed by designated stakeholders.

Release decision: Release readiness requires an explicit stakeholder decision. The PRD supplies business targets, but does not define all test pass thresholds (for example, exact load profile, browser-version policy, or allowed defect counts); confirm these before sign-off.
